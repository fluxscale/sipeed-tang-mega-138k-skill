# AE350 hard RISC-V subsystem

Use the vendor's Gowin RISC-V AE350 SOC hardware/software documentation and the [Pro `ae350_customized_demo`](https://github.com/sipeed/TangMega-138KPro-example/tree/main/ae350_customized_demo) as starting points. Verify applicability to the fitted GW5AST and target carrier. [Non-Pro issue #2](https://github.com/sipeed/TangMega-138K-example/issues/2) and [#7](https://github.com/sipeed/TangMega-138K-example/issues/7) are research leads for documentation/example requests, not proof of missing silicon functionality.

## Separate the layers

The hard processor subsystem, FPGA fabric, generated integration IP, debugger, firmware toolchain and board boot media have separate configuration requirements. An FPGA `.fs` image is not interchangeable with a firmware ELF/binary. Identify which memories hold code/data and which component loads each image.

Before building, establish exact CPU/ISA/ABI settings, SDK/compiler version, startup code, linker script, memory map, interrupt controller, timer, console UART, clocks/resets, debugger transport and boot source from the selected BSP. Do not infer them from the word “RISC-V,” nor substitute a generic soft-core example.

## Minimal bring-up

1. Reproduce the matching vendor hardware design and software example together.
2. Confirm processor clock/reset and required memory initialization before releasing execution.
3. Verify debugger attachment or a documented boot path; load the image into its intended region.
4. Use a UART banner and a known register read/write to establish execution. If silent, distinguish no execution, wrong UART routing/baud, early exception and a linker/boot mismatch.
5. Add timer/interrupt verification, then external memory and fabric peripherals one at a time.

Record PC/exception information where accessible. A UART banner alone proves neither DDR coverage nor coherent shared-memory operation.

## Fabric integration

Document the actual bus protocol and widths from the generated subsystem. Define address decoding, byte strobes, response/error behavior, ordering, alignment and endianness. Cross clocks through a supported bridge. Reset must not strand a transaction permanently waiting for a response.

For interrupts, identify edge/level semantics, synchronization, pending/clear behavior, routing and enable sequence. For shared buffers/DMA, establish cacheability, coherency, memory barriers, flush/invalidate operations and ownership. Two agents observing the same address do not necessarily observe each other's writes immediately.

Use volatile MMIO access through the BSP's facilities where appropriate; do not use C `volatile` as a substitute for cache maintenance or ordering guarantees.

## Operating-system requests

For “can it run Linux?”, determine the actual CPU configuration and MMU/privilege support, firmware/boot chain, memory availability, interrupt/timer drivers, device tree and kernel/BSP support. Point to a matching demonstrated software stack if one exists. Do not promise Linux merely because the chip has a RISC-V core and external RAM. Distinguish bare-metal, RTOS and Linux deliverables.

Before persistent boot updates, map FPGA configuration flash, firmware flash/regions, environment/configuration areas and recovery paths. Do not erase a combined image while treating it as a single-purpose FPGA bitstream.
